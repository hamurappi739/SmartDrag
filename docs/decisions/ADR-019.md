# ADR-019 — Payload identity uses preflight evidence plus authoritative OLE Drop revalidation

- **Status:** Accepted architecture; Explorer preflight mechanism remains Provisional
- **Date:** 2026-08-31

## Decision

SmartDrag distinguishes two levels of payload knowledge:

1. **Preflight eligibility** — enough to decide whether production overlay presentation is allowed. Current G2 experiment uses documented Explorer Shell automation (`ShellFolderView.SelectedItems`) mapped to the source Explorer top-level HWND.
2. **Authoritative payload** — the actual `IDataObject` delivered to `IDropTarget::Drop`, read as `CF_HDROP`.

The preflight path and authoritative Drop path must match for the single-file MVP. A mismatch returns `DROPEFFECT_NONE` and no action is committed.

`DragEnter` only checks whether `CF_HDROP` is available with `QueryGetData`; it does not render/extract the full Shell data object solely for hover feedback. Actual path extraction is deferred to `Drop`.

## Why

Explorer selection can race or differ from the object actually dropped. Conversely, waiting for `Drop` alone is too late to satisfy the canonical requirement that unsupported payloads should not cause normal overlay presentation.

Two-stage validation gives us conservative UX and authoritative execution.

## Provisional part

The exact mechanism used to acquire preflight paths is not accepted yet. The Shell automation experiment must pass G2 across Windows 10/11 Explorer windows, Windows 11 tabs, Desktop, hidden extensions, virtual folders, and selection races. If it fails, another documented and non-invasive evidence source must replace it without changing the two-stage contract.
