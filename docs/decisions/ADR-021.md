# ADR-021 — Native callback boundaries are no-throw and fail closed

Status: **Accepted**

## Context

SmartDrag receives callbacks from Win32/User32 accessibility events, a native window procedure, and OLE `IDropTarget`. Allowing a managed exception to escape any of these callbacks risks destabilizing the probe/process and, in the OLE case, interfering with the source application's active drag loop.

## Decision

All native-to-managed callback boundaries are treated as no-throw boundaries.

- WinEvent callback: capture primitive immutable signal data only; on failure drop the diagnostic signal and increment a counter.
- Window procedure: catch managed exceptions, record privacy-safe diagnostic type/HRESULT, and do not rethrow through User32.
- `IDropTarget` callbacks: catch managed exceptions, force `DROPEFFECT_NONE` when an effect exists, best-effort reset local hover state, and return `S_OK` to avoid claiming an operation that SmartDrag could not safely validate.
- Diagnostic logging after construction is best-effort/no-throw.
- Native-boundary failure logs must not contain raw source paths or exception messages.

## Consequences

A SmartDrag fault can cause a false negative (no overlay/no SmartDrag drop) but must not convert into a destructive or undefined native drag result. This is an implementation of the accepted fail-open-toward-native-drag and fail-safe-toward-user-files invariants.

Fatal process conditions are still outside any reliability guarantee; the policy is about ordinary managed exceptions and application faults.
