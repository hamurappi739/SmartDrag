# ADR-029 — Durable output recovery journaling is required before a reservation is issued

Status: **ACCEPTED**

## Decision

`PhysicalOutputManager.ReserveAsync` must persist a durable `OutputRecoveryRecord` before returning an `OutputReservation` to an action handler.

The record contains only:

- `ReservationId`;
- absolute SmartDrag temporary-output path;
- reservation timestamp.

It deliberately does not persist the source path or final path because startup crash cleanup does not need them.

If durable journaling fails, the reservation fails and image processing must not start.

The temporary filename must contain the exact reservation id:

```text
.<target>.smartdrag-<ReservationId:N>.partial<extension>
```

## Why

Without durable evidence, a process crash between creating/writing a partial and normal cleanup can leave orphaned data. Trying to discover such files later by wildcard scanning would give SmartDrag an unnecessarily broad deletion surface.

## Consequences

- recovery state becomes part of output correctness, not optional diagnostics;
- production composition must provide a durable journal implementation;
- tests may use the explicit in-memory journal;
- a stale journal record after a successful final move is safe because the recorded partial path no longer exists.
