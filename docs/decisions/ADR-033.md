# ADR-033 — Production startup order is single-instance -> crash recovery -> hooks/UI/runtime

Status: **ACCEPTED**

## Decision

Production startup must execute in this order:

```text
acquire named single-instance mutex
        -> open durable output recovery journal
        -> reconcile journaled stale partials
        -> compose OutputManager with same journal
        -> initialize runtime/jobs/actions
        -> register WinEvent/OLE/overlay integration
```

If another SmartDrag instance owns the mutex, the new process exits/does not initialize drag integration.

If the previous instance abandoned the mutex, the new owner proceeds to recovery before hooks are registered.

## Why

Startup recovery must not race a second live SmartDrag process that may still be writing a journaled temporary output.

## Current code

- `NamedMutexSingleInstanceLease` implements the process guard on a dedicated mutex-owner lifetime thread because Windows mutex ownership/release is thread-affine;
- `StartupSafetyBootstrap` implements the first three steps;
- `Program.Main` remains blocked until G0/G1/G2 are proven.

## Recovery failure gate

If recovery is not clean (unreadable journal, partial cleanup failure, or unresolved remaining record), `StartupSafetyBootstrap` returns `RecoveryBlocked` and `RuntimeMayStart=false`. Hooks/overlay/action runtime must not be registered in that state.
