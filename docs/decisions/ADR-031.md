# ADR-031 — Completion commands are capability-gated; generated-output deletion remains disabled in v0.7

Status: **ACCEPTED; v0.7 delete hold superseded by ADR-034**

## Decision

`CompletionModel.Commands` is built from the intersection of terminal job state, output ownership facts, and concrete runtime capabilities.

Current production-capability target:

- Open containing folder — allowed when Windows adapter is available;
- Copy result path — allowed only when the Windows completion composition supplies a real owner HWND; otherwise the capability is suppressed;
- Start result drag — disabled until a production OLE drag-source implementation is proven;
- Delete generated output — disabled until SmartDrag can verify strong file identity at deletion time;
- Dismiss — always allowed.

In v0.7 the Runtime executor clamped `CanDeleteGeneratedOutput=false`. ADR-034 supersedes that temporary hold with strong file-identity + handle-bound deletion; capability gating itself remains required.

## Why

Path equality plus historical `GeneratedOutputPaths` does not prove the file currently at that path is still the SmartDrag-created file. Another process/user can replace it between completion and deletion (TOCTOU). Exposing delete before identity-safe deletion would violate the source/data safety model.

## Required future gate

Before enabling delete, add an ADR and tests for Windows file identity / handle-based deletion or an equivalently strong mechanism. Never solve this with timestamp/size heuristics alone.
